# KAR Labs — Codex project instructions

## Purpose
KAR Labs is an Indonesian digital-services website. The current strategic focus is **Website Katalog Produk + Business Automation untuk UMKM**. Optimize for clarity, trust, qualified WhatsApp/contact leads, mobile usability, maintainability, and fast static deployment. See `docs/KAR_LABS_CONTEXT.md` for business goals and version-reconciliation notes.

## Current production architecture
- Production is **static HTML, compiled CSS and Vanilla JavaScript**, NOT the legacy React/Vite scaffold.
- `index.html`: homepage and offers.
- `catalog.html`: interactive service demos.
- `public/index.js`: homepage behavior.
- `public/catalog.css`, `public/catalog-*.js`: catalog styling and feature behavior.
- `styles/tailwind-theme.css`, `tailwind.config.js`: Tailwind source/theme configuration.
- `public/tailwind.css`: generated by `npm run build:css`; do not hand-edit it.
- `dist/`: generated deployment output; do not hand-edit or commit it.
- `src/`, `src/App.tsx`, `vite.config.ts`: retained legacy references, not the production entrypoint.
- `netlify.toml`: Netlify deploys using `npm run build`, publishes `dist/`, Node 20.

## Workflow
1. Read relevant source files and `README.md` for the task. Do not treat obsolete advice in `DEVELOPMENT_GUIDE.md` as the source of truth when it conflicts with production code.
2. Before the first feature edit, inspect and report repository status and reconcile the uploaded ZIP snapshot against GitHub `main` and Netlify deployment. The ZIP provided on 2026-11-17 documents a newer v2.9.0 Tailwind compilation flow; the public GitHub README/package observed that day reflected v2.8.0. Do not silently downgrade or overwrite either version.
3. Propose a concise task plan and targeted file list; keep changes minimal and focused.
4. Validate modifications with `npm run check`, then `npm run preview` for production-like smoke tests when possible. Test home/catalog, responsive layout, links/CTA, and touched interactions. Report what was and was not actually tested.
5. Use Git branches and inspect the diff. Do not push, merge to main, deploy, or change hosting settings without explicit user approval.

## Safety and content
- Never expose secrets or commit environment files/tokens. Get approval before new production dependencies, paid APIs, or external data collection.
- Do not invent customer testimonials, portfolio projects, sales outcomes, visitor counts, guarantees, or factual claims. Mark examples/demo data transparently.
- Preserve accessibility, SEO metadata, security headers, and current behavior unless a change is explicitly requested.
- Respond in Bahasa Indonesia unless the user requests otherwise.
